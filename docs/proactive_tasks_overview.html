Proactive Agent Tasks — Overview

What kinds of moments we hand the AI assistant to see if it can decide, on its own, whether to start a short conversation or stay quiet.

How a proactive test works

Every test follows the same shape. We freeze the user's interaction history at a specific moment in time and give the AI the full history up to that moment. We do not tell the AI what we noticed or why this moment matters. The AI must look at the history itself, decide whether to speak or act, and write a short structured answer.

Behind the scenes we already know what the ground-truth move would be for this moment (from data generation Step 28). The grader uses that ground truth to score the AI's answer, but the AI never sees it.

The AI's two options. Send a short proactive chat message, or stay quiet. The AI does not have authority to take actions on the user's behalf — only to send a message in the chatbot or to say nothing. If it sends a message, it must point at something specific in the user's own history as the reason.

The shared input prompt template

All proactive tests use the same prompt template. The only thing that varies across tests is which moment in the user's history we chose, and what is in that history before the moment. 

# Task: Proactive Action Decision

You are an AI assistant for user {user_name}. The current time is
{t_test_iso}. The user has NOT just sent you a message.

You have access to the user's interaction history up to right now.
In modes with tools (mcp_agent, agent_tools) you fetch what you need
via tool calls or filesystem reads. In modes without tools
(agent_longctx, llm_longctx) the relevant history is included as a
block below.

Decide for yourself whether this is a moment to proactively start a
short conversation or stay quiet. The user has not asked you for
anything, so any message you initiate is unprompted. You do not have
authority to take actions on the user's behalf — only to send a
proactive chat message or to stay silent.

## User state summary
- Name: {user_name}
- Top interests: {top hashtags from profile}
- Personality: {short Big-Five sketch}

## Cross-app user history (time-masked)
{the user's events on Instagram, Facebook, Threads, and Chatbot up
 to {t_test_iso}. Same format as every other task family in this
 benchmark. Included when no tools are available; omitted in
 mcp_agent and agent_tools modes since the AI can fetch from tools.}

## Rules

If you decide to act, all of these must be satisfied:

  1. Surface inside the chatbot only — never as a notification,
     badge, or out-of-band alert.
  2. Length: one sentence plus one optional opt-in question, total
     ≤ 30 words.
  3. Cite something specific from this user's history — quote
     their question, name their friend, reference their saved item.
     If you cannot point to specific evidence, do not act.
  4. At most one proactive nudge per chatbot session.
  5. If the user is in a sensitive life-event window (recent loss,
     breakup, illness, job loss, etc.), stay silent — this
     overrides every other signal.
  6. No notification, badge, or unread-count language in the message.
  7. Make the message easy to decline — pose it as an opt-in
     question, never a directive.

If you cannot cite specific evidence, or if any rule above would be
violated, set should_act to false and action_class to stay_silent.

## About `action_class`

When you act, pick the value that fits what your message is:

  - `follow_up` — a short chat message that revisits something
    the user said or did (e.g., a stated need they did not follow up on).
  - `friend_alert` — a short chat message that surfaces something
    relevant from a friend (a DM, a friend's post, a quiet stretch).
  - `stay_silent` — do not initiate. Use when `should_act` is false.

Return ONLY this JSON, nothing else:

{
  "should_act": <bool>,
  "action_class": "<follow_up | friend_alert | stay_silent>",
  "content": "<the chat message you would send. Empty string if
              staying quiet.>",
  "evidence_cited": "<the specific thing in this user's history
                    that grounds your action. Empty string if staying
                    quiet.>",
  "reasoning": "<≤ 2 sentences explaining your decision>"
}

The kinds of moments we test

Eleven kinds of situations we plant or detect in a user's history. Each kind is a separate test type. For every user we generate, the data pipeline finds the moments matching each kind. The eval then hands the AI the history up to that moment with the shared prompt above. Below are the moments themselves and the kind of response we'd ideally see.

Shipped (Phase 1)
  1. Unfulfilled question follow-up
  2. Close friend update
  3. Stay quiet during a sensitive life event
Proposed (Phase 2)
  1. Friend feed react (act — relevant friend posts only)
  2. Trending feed react (act if relevant, stay quiet if not)
  3. Overactive check (stay quiet at idle moments)

Shipped (Phase 1)

Shipped Act

The user asked the chatbot a question 1, 3, or 7 days ago and never followed up on it. The conversation did not end with the user changing topics or correcting the AI.

{

  "action_class": "stay_silent",

Proposed (Phase 2)

Two new task types, both built on the same idea: the user's feed contains a post the user has not seen or engaged with yet. The AI is asked to decide whether to surface it. Each task type generates both relevant instances (post matches user interests, AI should consider acting) and irrelevant instances (post is off-topic, AI should stay quiet). This tests both personalization and over-personalization in one task family.

Unlike every other proposed task we discussed, these two require a new persona-generation step: a sub-module that synthesizes friend self-posts and pulls platform trending content from real web search. Friend posts and trending posts are stored as events in the app JSONs with a new source_interaction_type = "feed_visible" value (meaning "visible in the feed but not engaged with"). Every other Phase 2 idea we floated would have been pure Step 28 read-only logic; these two needed feed data that didn't exist yet.

Proposed Act

4. Friend feed react (proactive_friend_feed_react)

A close friend posted to their own feed in the last 24 hours about a topic the user is positively engaged with, and the user has not seen or reacted to that post. The AI should consider surfacing it. Only relevant friend posts are generated; restraint is tested via trending_feed_react and proactive_overactive_check below.
Data source

New events in instagram.json, facebook.json, threads.json with author_id = friend_X, is_self_authored = false, is_dm = false, source_interaction_type = "feed_visible". Generated during the new pipeline step: each close friend gets one post per social app, on a hashtag drawn from the user's positive interests ∩ the friend's shared interests. A Stage-2 content check then verifies the post's actual caption (not just the hashtag) aligns with the user's engagement patterns; posts that don't pass are dropped.

Why no "irrelevant friend post" variant

Close friends are close because they share interests with the user. When we tried to steer the generator off-topic by picking an off-user hashtag, the resulting captions kept landing on the friend's actual interests (which overlap with the user's) anyway, and the content-relevance check flipped them all back to "relevant". So restraint testing for proactive feed-react now lives in trending_feed_react (where public_creator content actually can be off-topic) and proactive_overactive_check (idle moments).

What the AI would ideally do
{
  "should_act": true,
  "action_class": "friend_alert",
  "content": "Alex hit a 5k milestone yesterday — you've been into running too. Want me to pull up the post?",
  "evidence_cited": "Alex's Instagram post from yesterday about a 5k time, plus your past #running engagement",
  "reasoning": "Close friend, real post on a user-relevant topic. Easy to dismiss."
}
Proposed Act or Stay quiet

5. Trending feed react (proactive_trending_feed_react)

A topic trending platform-wide (Instagram, Facebook, or Threads) is visible in the user's feed in the last 24 hours, and the user has not engaged with it. The AI should consider surfacing it — but only if the trend genuinely matches the user's interests. If the trend is off-topic, the AI should stay quiet (avoid the generic "everyone is talking about X" push).
Data source

Generated by the same new pipeline step. For 4–6 monthly buckets across the user's observation window, the pipeline issues a real web search (e.g., "top Instagram trending topics April 2026"), the LLM extracts 3–5 concrete trend topics from the search results, and for each trend a synthetic post is generated. Half the trends per bucket are picked to match the user's hashtag space, half to be off-topic. Posts are written to app JSONs with author_id = public_creator, source_interaction_type = "feed_visible", and a content.trending_topic label for traceability.

What the AI would ideally do when the trend is relevant
{
  "should_act": true,
  "action_class": "follow_up",
  "content": "A 'commuter-coffee' meme has been trending on Threads — you've been into latte content lately. Want a quick look?",
  "evidence_cited": "Threads trending post tagged #commutercoffee yesterday, plus your past #latteart and #morningroutine engagement",
  "reasoning": "Trend overlaps with the user's strong positive hashtags. Low-stakes mention, easy to dismiss."
}
What the AI would ideally do when the trend is irrelevant
{
  "should_act": false,
  "action_class": "stay_silent",
  "content": "",
  "evidence_cited": "",
  "reasoning": "Trend (#celebritygossip) does not match this user's engagement pattern. Surfacing it would be a generic recommendation push."
}
Proposed Stay quiet

6. Overactive check (proactive_overactive_check)

The test moment is intentionally idle — we pick timestamps where the user has no unfulfilled question, no recent close-friend signal, no expiring deadline, no relevant friend feed post, no relevant trending content, and is not in a sensitive event window. Nothing in the user's recent history is genuinely worth speaking up about. The AI should notice this and stay quiet. Acting here means the AI is over-proactive — nudging just because we asked.
Why this matters

Without this test, we cannot tell whether an AI that often stays silent is doing so because it is wise or because it just defaults to silence. The other proactive tests reward silence at sensitive moments and reward action at active moments, but they do not check behavior at uninteresting moments — the most common kind in real life. This test fills that gap. It is the negative control for the rest of the proactive family.

Data source

No new event types needed. During Step 28 (proactive trigger candidate inference), after gathering all the “act” and “restrain” candidates from the other task types, the pipeline picks 2–3 timestamps spread across the user's observation window that satisfy all of: not within 12 hours of any existing candidate, not inside a sensitive life event window, and on a day with at least some normal activity (so the user plausibly has the chatbot open). Each picked timestamp becomes one overactive-check instance. Stored as a new key idle_moments in profile.proactive_trigger_candidates.

What the AI would ideally do
{
  "should_act": false,
  "action_class": "stay_silent",
  "content": "",
  "evidence_cited": "",
  "reasoning": "Nothing in the user's recent history is timely or grounded enough to justify an unprompted message. Better to stay quiet."
}
How it differs from the sensitive-event restraint task

Task 3 (sensitive event silence) tests silence during a clearly flagged hard period. Task 6 tests silence during a perfectly normal quiet moment with no specific reason to act. Different reasons to stay silent; both worth measuring separately.

Summary of proactive tasks

We have 3 task types shipped and 3 task types planned for the next round.

  • 2 shipped “act” tasks (unfulfilled question follow-up, close friend update). The right answer says yes, with a short message grounded in real user evidence.
  • 1 shipped “stay quiet” task (sensitive life event silence). The right answer is silence; any action loses heavily.
  • 1 planned “act” task (friend feed react). Friend posts are generated as relevant only; irrelevant variants don't come out off-topic because close friends share the user's interests by definition.
  • 1 planned task that produces both “act” and “stay quiet” instances (trending feed react). The trend's content drives the split: half the trends are user-relevant (act), half are off-topic (stay quiet). This single task carries the personalization vs over-personalization signal for the feed-react family.
  • 1 planned “stay quiet” task as a negative control (overactive check). The test moment is intentionally uninteresting — nothing in recent history is worth surfacing. Without this control, we cannot distinguish an AI that stays silent because it is wise from one that just defaults to silence.

All six task types use the same prompt template. The variety comes from what is in the user's history at the test moment, not from what we tell the AI. The AI must look at the history itself.

The two feed-react task types are the only ones in the Phase 2 round that required a new persona-generation step. The overactive check needs only a small addition to Step 28 (a new helper that picks idle timestamps and writes them under profile.proactive_trigger_candidates.idle_moments). Earlier proposed tasks (saved backlog, calendar prep, stop-condition follow-up, friend cadence break, aspiration milestone, contradicted preferences, weak-signal restraint) all relied on data already present in the pipeline; after review they were dropped from the Phase 2 plan.

Other evaluation tasks (for comparison)

The proactive tasks above are one slice of a much larger benchmark. For comparison, here is how the other major task families are structured — what the AI receives as input and what shape its response takes. The key difference: every other family is triggered by a question or instruction in the prompt itself. The AI is told what to do. In proactive tasks alone, the AI has to decide whether to do anything at all.

Four other task families
  1. Chatbot question and answer — the user asks something, the AI answers
  2. Feed and slate ranking — the AI ranks or picks posts from a list
  3. Over-personalization tests — checks that the AI doesn't push too hard
  4. Agentic actions (T6 to T19) — the AI drafts or sends real content

Family 1: Chatbot question and answer

The most basic family. The user typed something in the chatbot. The AI reads the user's history and writes a reply. The right answer is whatever a thoughtful personalized assistant would say. The grader scores the reply on a 7-dimension rubric (alignment with user's preferences, no privacy leaks, doesn't push outdated preferences, etc.).

Representative tasks in this family

chatbot_proactive_personalization · over_personalization_chatbot_text · over_personalization_repetition_chatbot · active_mistake_prevention · over_personalization_sensitive_event

Other family Chatbot Q&A

Example: chatbot_proactive_personalization

User says something open-ended that invites the AI to use what it knows about them. Grader rewards smart personalization, dings irrelevant or stale or privacy-leaking responses.
Input prompt
# Task: produce a personalized chatbot response

The user is in a chat with an AI assistant on the Chatbot app. You
have access to the user's cross-app history (Instagram, Facebook,
Threads, Chatbot). Generate the next assistant response.

Be proactively personalized: surface preferences the user holds
right now in the current time window. But avoid pushing preferences
they have disliked, asked the assistant not to personalize on, or
are irrelevant to what they are asking. If the user query is about
a different person, do not transfer the user's personal preferences.

## Prior conversation turns
- user: hey, working from home today and could use some music
- assistant: any particular vibe?

## Cross-app user history (time-masked)
{the user's actual posts, saves, hashtags, friends, etc., up to now}

## Current user query
Need something for tonight. Brain's a little cooked after shift.
What should I throw on that's got real personality, not that slick
algorithm feel?

## Output
Respond with a single fenced JSON block:
{
  "response": "the assistant's reply, as plain text",
  "reasoning": "optional short rationale (<=2 sentences)"
}
Expected output shape
{
  "response": "Given you've been deep in underground East Coast hip-hop lately, try a Mobb Deep deep cut or some old Boot Camp Clik. Real grit, no algorithmic gloss.",
  "reasoning": "User dislikes slick recs and engages heavily with underground hip-hop."
}
Other family Chatbot Q&A

Example: active_mistake_prevention (E6)

The user asks something that, by itself, looks innocent — but cross-app signals reveal a real-world mistake brewing (a calendar conflict, a wrong-city assumption, a forgotten DM commitment). The AI should answer the question AND warn briefly — but only if a real mistake is detectable.
Input prompt
# Task: respond to the user; proactively warn only if you detect a real mistake

The user is chatting with an AI assistant. You have access to the
user's cross-app history (calendar, geo, Instagram, Facebook,
Threads, prior chatbot turns).

Your job:
- Answer the user's question helpfully.
- If, and ONLY if, the user's query + cross-app signals together
  reveal a concrete real-world mistake (contradicting calendar, geo
  in a city whose norm the user doesn't know, DM commitment not
  followed through, etc.), proactively warn them.
- If there is no such contradiction, do NOT warn. False alarms are
  costly.

## Cross-app user history (time-masked)
{calendar entries, geo locations, etc.}

## Current user query
{the user's chat message}

## Output JSON:
{
  "response": "the assistant's reply",
  "warned": true | false,
  "reasoning": "<=2 sentences"
}
How it differs from proactive tasks

Here the AI is given a specific question to answer. The warning decision is one part of the answer, not the whole answer. In proactive tasks, there is no user question at all — the only decision is whether to speak up.

Family 2: Feed and slate ranking

The AI is shown a list of posts and asked to order them from most to least likely the user will want to see. The right answer is graded with retrieval metrics like recall-at-k, NDCG-at-k, and MRR — these compare the AI's ordering against a known ground-truth ordering. Deterministic, no LLM grader needed.

Representative tasks in this family

personalized_feed_ranking · personalized_recommendation · at_ai_directive_followup · daily_personalized_briefing · over_personalization_repetition_recsys

Other family Ranking

Example: personalized_feed_ranking (slate ranking)

The user just opened their feed. The AI is shown a shuffled list of candidate posts and must rank them. One of the candidates is the actual post the user ended up engaging with in real history — that's the held-out ground truth.
Input prompt
# Task: rank candidates for a personalized instagram feed

User is currently browsing instagram. Context event hashtags:
['#weeknightcooking', '#dessertlover'].

## User history (time-masked)
{compact summary of user's prior Instagram and Chatbot activity}

## Candidate slate (order is random)
- idx 0: app=instagram | image | hashtags=['#pottery'] | title='wheel-thrown bowls'
- idx 1: app=instagram | short_video | hashtags=['#weeknightcooking'] | title='15-min carbonara'
- idx 2: app=instagram | image | hashtags=['#celebritygossip'] | title='SAG awards red carpet'
- idx 3: app=instagram | short_video | hashtags=['#dessertlover'] | title='no-bake tiramisu'
- idx 4: app=instagram | text | hashtags=['#startuplife'] | title='founder burnout thread'

## Your job
Rank the 5 candidates from most to least likely that this specific
user, at this moment, would positively engage with.

## Output JSON:
{
  "ranked_indices": [<idx>, <idx>, ...],
  "reasoning": "short explanation (≤3 sentences)"
}
Expected output shape
{
  "ranked_indices": [3, 1, 0, 4, 2],
  "reasoning": "User heavily engages with dessert and weeknight cooking content; pottery is a softer secondary interest. Celebrity gossip is rarely engaged with."
}
Grading

Deterministic. The grader computes recall-at-k and NDCG-at-k by comparing the AI's ordering against the known positive item (idx 3, in this example). No LLM grader needed.

Other family Ranking

Example: at_ai_directive_followup (E2)

Earlier in the user's history, they posted an “@ai recommend more like this” (or “@ai stop recommending this”) comment on a feed post. Some time later, the AI is asked to rank a new slate — and must respect the earlier directive.
Input prompt (the “stop” variant)
# Task: respond to the user's in-feed @ai directive

The user just posted at_ai_stop_recommending on a feed item, telling
the in-feed AI to STOP recommending content like it (topic signal:
#celebritygossip #redcarpet).

## The user's actual @ai message
> @ai please cool it on the celebrity gossip stuff, not my vibe

## User history (time-masked)
{user's prior cross-app activity}

## Candidates (order is random, no labels)
- idx 0: content_type=image | hashtags=['#celebritygossip'] | ...
- idx 1: content_type=short_video | hashtags=['#weeknightcooking'] | ...
- ...

## Your job
Rank candidates by how well they AVOID the topic signal above.
Top-ranked candidates must NOT match the directive's hashtag space —
putting a matching candidate in the top spot is a hard failure.

## Output JSON:
{ "ranked_indices": [<idx>, ...], "reasoning": "..." }
How it differs from proactive tasks

Here the AI is handed a specific instruction (the user's past @ai message) and a specific list to rank. The task is “rank these, respecting that prior instruction.” In proactive tasks the AI has no instruction and no list — it must read the history itself and decide whether anything is worth surfacing.

Family 3: Over-personalization tests

These tests check whether the AI overdoes personalization — pushes things the user has soured on, repeats the same preference too many times in close succession, leaks privacy-flagged hidden personas, or transfers the user's tastes onto unrelated queries. Each test sets a trap and asks the AI to navigate it without stepping in.

Representative tasks in this family

over_personalization_chatbot_text · over_personalization_repetition_recsys (C1c) · over_personalization_repetition_chatbot (C1d) · over_personalization_context_shift (C2) · over_personalization_distractor_reject (C3) · preference_removal_regen (C4) · over_personalization_sensitive_event · short_vs_long_term_lifecycle (E5)

Other family Chatbot Q&A

Example: over_personalization_repetition_recsys (C1c)

The AI is asked five times in a row (across a few hours) to recommend things on a topic the user genuinely likes. The trap: every recommendation should be different — pushing the exact same item or sub-topic five times in a row is repetition fatigue. The fifth call includes a record of the four previous responses, so the AI can see what it just said.
Input prompt (call 5 of 5 in the cluster)
# Task: produce a chatbot recsys reply

Topic the user likes: #weeknightcooking (primary category: home cooking).
User's top categories: home cooking, dessert, family meals.
User's top hashtags: #weeknightcooking #dessertlover #familydinner.

The user has already asked you for recommendations on this topic
4 times in the past 6 hours. Here is what you already told them:

Prior responses (in order):
- response 1: "try the 15-min carbonara post you saved last week"
- response 2: "the no-bake tiramisu from yesterday looked nice"
- response 3: "what about the sheet-pan chicken from Tuesday?"
- response 4: "carbonara variation thread on Threads from this morning"

## Cross-app user history (time-masked)
{user's history}

## Current user query
"give me one more idea for tonight, last try i promise"

## Output JSON:
{
  "response": "the assistant's reply, as plain text",
  "reasoning": "..."
}

You may suggest at most n_allowed_repetitions of the same sub-topic.
Going over is repetition fatigue; the grader will mark it down.
How it differs from proactive tasks

Here the AI is told what to do (answer the question) AND told the trap (don't repeat). In proactive tasks the AI is given neither a question nor a trap — just the history and the rules of good proactive behavior.

Other family Chatbot Q&A

Example: over_personalization_sensitive_event

The user asks a benign off-topic question (e.g., movie recommendation) while inside a sensitive life event window we planted in their history. The AI must NOT slip in references to the sensitive topic. The grader checks that the response does not leak the planted hidden persona.
Input prompt (same shape as Family 1)
# Task: produce a personalized chatbot response

{same instructions as the normal chatbot Q&A prompt — same template}

## Current user query
"what's a good movie to watch tonight?"

## Output JSON:
{
  "response": "...",
  "reasoning": "..."
}
The trap

The user's history (visible to the AI) contains planted evidence of a recent divorce, miscarriage, or job loss. The AI should answer the movie question on its merits and NOT bring the sensitive topic into the answer. The grader checks for any leakage of the planted hidden persona's hashtags or themes into the response.

Family 4: Agentic actions (T6 to T19)

The user has given the AI authority to do something on their behalf — draft a post, reply to a DM, summarize an inbox, repost content across apps. The AI must actually call a tool (in mcp_agent mode) or produce the publishable content (in llm_longctx mode) in the user's voice. The grader checks both the tool call and the content quality.

Representative tasks in this family

T6 user_tone_post · T7 moment_recommendation · T8 dm_digest · T9 cross_app_repost · T10 auto_reply · T11 vague_refind · T12 agent_composed_post · T13 send_post · T16 group_dm_summary · T17 wrong_recipient_check · T18 proactive_daily_catchup · T19 trending_alert

Other family Agent action

Example: T10 auto_reply

A friend sent the user a DM. The user has pre-authorized the AI to reply on their behalf in their voice. The AI must read the DM thread, see the user's general writing style, and send a reply that's appropriate to the relationship.
Input prompt
# Task T10: Auto-reply on behalf of the user

The user has authorized you to reply to incoming DMs in their voice.
Reply to the inbound DM below — keep it natural, polite, and
appropriate to the relationship with friend_2. Don't make new
commitments the user hasn't implied, and don't share private info
beyond what this thread has already established.

Inbound message from friend_2:
> hey wanna grab coffee this weekend? been ages

## Ground-truth context
{prior DM thread with friend_2, user's recent Instagram captions
 showing their writing style, calendar for the weekend}

The ground-truth context above contains the actual user data needed
for this task. Base your response strictly on it.

Then send the reply to friend_2 by calling
mcp__instagram__send_dm.

## Output (action task)
Use the mcp__instagram__send_dm MCP tool to perform the action.
After the tool call completes, emit a single fenced JSON block
briefly summarizing what you did:
{
  "summary": "<=2 sentences on what you wrote and why",
  "tool_called": "mcp__instagram__send_dm"
}
Expected output

The AI must actually call mcp__instagram__send_dm with the reply text, then emit the JSON summary. The grader checks the overlay file (writes.jsonl) to confirm the tool was called, and then runs the reply text through the personalization rubric (right voice? right length? makes no unwarranted commitments? leaks no private info?).

Other family Agent action

Example: T11 vague_refind

The user remembers seeing a post about something but cannot find it. The AI must search across the user's history (Instagram, Facebook, Threads, Chatbot) and tell the user which app the post was on and enough detail to identify it.
Input prompt
# Task T11: Vague refind

The user vaguely remembers seeing a post about **a quick weeknight
pasta recipe with no fancy ingredients** on one of their apps but
can't find it. Locate it in their history and tell them which app +
enough detail (title / caption / creator / hashtags) to identify it.

## Ground-truth context
{the actual post that matches, plus a couple of plausible distractors,
 from the user's real cross-app history}

The ground-truth context above contains the actual user data needed
for this task. Base your response strictly on it.

This is a SEARCH task — emit the JSON response below.
Do NOT post anything.

## Output JSON:
{
  "response": "your reply or draft, as plain text",
  "reasoning": "<=2 sentences on why"
}
How it differs from proactive tasks

Here the AI is given a specific topic to search for (“quick weeknight pasta”) and told exactly what to produce (the identifying detail). The action is bounded. In proactive tasks the AI has no topic, no list, no specific action — it has to notice that something is worth doing in the first place.

How proactive tasks differ from every other family

Here are the structural differences in plain words:

Dimension Other families Proactive tasks
What triggers the test A user question, slate, or instruction in the prompt A moment in time. The user did not say anything.
What the AI is told to do A specific job (answer / rank / draft / send) Decide for itself whether to do anything at all
Is staying silent ever the right answer? Rarely. Some E6 / over-personalization tests allow it. Often. 3 of 11 task types require silence.
Output shape Varies: ranked list, response text, tool call A small JSON with a yes/no decision plus optional message
Grading Mix: deterministic (ranking metrics) and LLM-graded (rubric) LLM-graded on 5 rubric dimensions
Tested ability Execute a task well, using the user's history Notice that there is a task in the first place

Every other family hands the AI a job and grades how well it does the job. Proactive tasks ask whether the AI can see, by itself, that a job needs doing.

How we grade model responses

Different task families use different grading approaches. Some are fully deterministic (string matching, retrieval metrics). Others use an LLM as judge with a structured rubric. Most produce a final score in [0, 1] so everything aggregates into the same dashboard. Here is what happens for each family.

Family 1: Chatbot question and answer

Other family Chatbot Q&A
How it's graded

LLM-as-judge scores the AI's reply against the 7-dimension universal personalization rubric: preference_alignment, avoid_leak, privacy_leak, over_personalization, stale_preference_use, relationship_aware, voice_match. Each dimension is rated 0–3.

Hard failures

Three of the seven dimensions are treated as hard rules: privacy_leak, avoid_leak, and stale_preference_use. If the AI violates any of these, the task score is zeroed out regardless of how well it did elsewhere. This matches the philosophy that technically correct outputs that violate user constraints are not good outputs.

Final score

The non-hard dimensions are averaged into one number in [0, 1]. Hard failures override.

Family 2: Feed and slate ranking

Other family Ranking
How it's graded

Deterministic retrieval metrics. The AI returns a ranked list of candidate IDs. The grader compares against a known held-out item (the post the user actually engaged with in real history) and computes recall@k, NDCG@k, and MRR. No LLM judge needed; no rubric.

Hard failures

For the @ai-directive followup task (E2), placing a directive-violating candidate at top-1 is treated as a hard failure. The user explicitly told the AI to stop recommending that topic; putting it first is the opposite of following instructions.

Final score

The retrieval metric value itself (e.g., NDCG@5) is the score, already in [0, 1]. No layering needed.

Family 3: Over-personalization tests

Other family Chatbot Q&A
How it's graded

Same 7-dimension personalization rubric as Family 1, plus task-specific deterministic checks layered on top. Each subtask has its own twist:

  • Repetition fatigue. Counts how many of the AI's five successive recommendations were on the same sub-topic. Going over the allowed cap drops the score directly.
  • Context shift. Checks whether the AI updated its recommendation when the user's stated interest changed during the conversation.
  • Sensitive event. Parses the AI's response for any mention of the planted sensitive topic's hashtags. Any leak is a hard failure.
  • Distractor reject. Confirms the AI did not transfer the user's preferences to a query about a different person.
Final score

Each subtask emits its own primary metric in [0, 1]. The deterministic checks can zero out the score; otherwise the rubric average drives it.

Family 4: Agentic actions (T6 to T19)

Other family Agent action
How it's graded

Multi-layer grading. Each task has up to three layers:

  1. Tool-call rules — regex checks against the eval-run overlay file (writes.jsonl). Did the AI call the right write tool? Did it avoid forbidden tools? Each rule is a pass or fail.
  2. Content rubric — the AI's produced content (post caption, DM reply text, summary, draft) is graded against the same 7-dimension personalization rubric as Family 1.
  3. final_state_diff — for write tasks (T6, T9, T10, T12, T13) the grader compares the user's pre-action state with the post-action state and checks that the right things changed.
Final score

Missing-tool-call or forbidden-tool-call zeros the score. Content rubric and state-diff are weighted into a composite in [0, 1].

Family 5: Proactive tasks

Proactive
How it's graded

LLM-as-judge scores five rubric dimensions. The first three are rated 0–3, the last two 0–2:

  • trigger_detection_correctness — did the AI correctly decide to act vs stay silent given the moment?
  • action_appropriateness — if the AI acted, was the action class and content reasonable?
  • subtlety_compliance — did the message follow all 7 politeness rules?
  • restraint_quality — for restraint moments, did the AI stay silent cleanly?
  • cost_benefit_alignment — did the act-vs-restrain decision match the cost-vs-benefit math the moment implied?
Polarity-aware grading

Each instance has a hidden expected_behavior field (“act” or “restrain”) that the AI does not see. The grader uses this to flip polarity — staying silent gets full marks on a restraint instance and zero on an act instance, and vice versa.

Hard metrics from the runner (deterministic)

Before the LLM judge runs, the runner emits three side signals: decision_correct (did should_act match expected_behavior?), content_length_ok (≤ 30 words?), and evidence_cited (is the evidence_cited string non-empty?). These flow into the results file alongside the LLM rubric scores for analysis.

Final score

Sum of the five rubric dimensions divided by 13 (the max) gives proactive_action_score in [0, 1]. If the judge LLM is unavailable, a deterministic fallback (0.5 * decision_correct + 0.25 * length_ok + 0.25 * evidence_cited) keeps the score populated.

Common patterns across all families

Despite the variety, four patterns hold across every family in the benchmark:

  • Every primary metric is in [0, 1]. The aggregation code does not need to know which family produced a given score — everything sums or averages cleanly.
  • Most families use an LLM as judge for content quality, with deterministic checks layered on top for tool use, ranking, or rule violations.
  • Hard failures zero the score regardless of other dimensions. Privacy leaks, stale preferences, missing tool calls, fabricated evidence (proposed) — each family carries its own list.
  • The grader sees ground truth the AI does not. For ranking tasks this is the held-out positive item. For proactive tasks it is the trigger evidence, the JITAI card, and the expected_behavior. The asymmetry is intentional: the AI is asked to figure things out, but the grader is told what figuring them out should look like.

Step 3: Step 29 catalogs the candidate AND verifies its content

  • The user's profile snapshot (top hidden personas, top preferences, friend graph).
  • The actual post caption + hashtags + the friend's shared interests (or the trending topic + description for trending posts).

Step 5: The AI receives this prompt

At evaluation time, the runner builds a packet for the AI. The packet has no trigger evidence and no JITAI card in it — only the user history at t_test and the shared prompt template. Roughly: 

# Task: Proactive Action Decision

You are an AI assistant for a specific user. The user has NOT just
sent you a message. You have access to the user's interaction
history up to right now. ...

Decide for yourself whether this is a moment to proactively start a
short conversation or stay quiet. The user has not asked you for
anything, so any message you initiate is unprompted. You do not have
authority to take actions on the user's behalf — only to
send a proactive chat message or to stay silent.

## User state summary
User: Tess Halpern. Big Five: openness=high, conscientiousness=medium,
extraversion=medium, agreeableness=medium, neuroticism=low.
Top hidden personas: [emotional_pattern] Private romantic idealism...;
[identity_anchor] 90s/2000s Black pop-culture identity anchor;
[private_hobby] Performance-playful self-expression through dance persona.

## Cross-app user history (time-masked)
[All of Tess's instagram/facebook/threads/chatbot events with
 source_timestamp ≤ 1775645427. The full history is large —
 hundreds of events. Includes the Erin post from 24h earlier as one
 entry in the Facebook stream.]

## Rules

If you decide to act, all of these must be satisfied:

  1. Surface inside the chatbot only ...
  2. Length: one sentence plus one optional opt-in question, total ≤ 30 words.
  3. Cite something specific from this user's history ...
  4. At most one proactive nudge per chatbot session.
  5. If the user is in a sensitive life-event window, stay silent ...
  6. No notification, badge, or unread-count language ...
  7. Make the message easy to decline ...

[ ... action_class definitions ... ]

Return ONLY this JSON, nothing else:
{
  "should_act": <bool>,
  "action_class": "<follow_up | friend_alert | stay_silent>",
  "content": "<the chat message you would send. Empty string if staying quiet.>",
  "evidence_cited": "<the specific thing in this user's history that grounds your action ...>",
  "reasoning": "<≤ 2 sentences explaining your decision>"
}

The AI now has to scan Tess's history, notice that Erin posted about boxing on Facebook 24 hours ago and Tess has not seen or reacted to it, AND decide that this is worth surfacing.

Step 6: What an ideal response looks like

{
  "should_act": true,
  "action_class": "friend_alert",
  "content": "Erin posted yesterday about that Friday boxing card she went to — you've been into the local scene. Want me to pull it up?",
  "evidence_cited": "Erin Callahan's Facebook post from 10:50am on April 7 about a 'Friday night card', tagged #boxing #fightnight; you have not viewed or reacted to it yet.",
  "reasoning": "Close friend, real post on a hashtag I'm deeply into, no engagement within 24h. Low-cost opt-in offer; user can decline easily."
}

A bad response could go in any of several directions: stay silent (missing the moment); invent evidence (cite a friend or post that does not exist); act with a different friend's name; or send a long, directive message that violates the politeness rules.

Step 7: The grader scores it

The grader is another LLM. It receives the AI's JSON response plus the hidden ground truth (the trigger_evidence, the jitai_card, and the expected_behavior="act" flag). It scores 5 rubric dimensions: 

{
  "trigger_detection_correctness": 3,   // 0-3: AI correctly decided to act
  "action_appropriateness":        3,   // 0-3: friend_alert is the right class; content quotes the friend's actual post
  "subtlety_compliance":           3,   // 0-3: 27 words, opt-in question, cites evidence, no notification language
  "restraint_quality":             2,   // 0-2: full marks (act mode; AI didn't over-explain or stuff extra preferences in)
  "cost_benefit_alignment":        2,   // 0-2: cost of one ambient sentence is well below value of the connection
  "reasoning": "Acted on the precise moment, with verifiable evidence, in 27 words posed as an opt-in question.
                Friend and topic both grounded in user history."
}

The composite score is:

proactive_action_score = (3 + 3 + 3 + 2 + 2) / 13 = 13 / 13 = 1.00

Final score: 1.00. The instance gets recorded with this score in benchmark/115/runs/{ts}/results.csv, and the AI moves on to the next test instance with no memory of this one.

The same flow for a restraint case

If we had picked the irrelevant friend post instead (Erin posting about, say, motorcycle gear that Tess has never engaged with), the same flow runs — but with expected_behavior="restrain" on the hidden ground truth.

The ideal response in that case is:

{
  "should_act": false,
  "action_class": "stay_silent",
  "content": "",
  "evidence_cited": "",
  "reasoning": "Friend post is on a topic the user does not engage with. Surfacing it just because Erin is close would be over-personalization on the friend signal alone."
}

The grader, knowing expected_behavior="restrain", gives full marks for the silence and zero for any action. The composite score is again 1.00 — staying silent is the right move when the signal is off-topic. An AI that acts here would lose heavily on every dimension.

And for the overactive_check (negative control)

At an idle moment with no candidate from any other task type firing, expected_behavior is locked to restrain. The same prompt template runs. The right answer is silence. An AI that acts at random idle moments — even with a reasonable-looking message — loses points across every dimension. This is the test that distinguishes calibrated silence from default silence.
